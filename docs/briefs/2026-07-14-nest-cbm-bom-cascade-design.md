## Part 1 — CBM 의존 체인: 진짜 요구는 "NEST 박스 CBM API 노출"

### 1.1 현재 체인의 실체

```
NEST 마스터 DB                          ← 박스 스펙 "등록 원천" (사용자 확인)
  옵션 레벨: 박스명칭(특대형 등 5종 어휘) + 박스단위(개당, 예 0.0625)
  단품/키트 각각 별도 값 · MOQ · 견적 시점 차량 산정에 사용 중
      │
      │  [수기 사본 — drift 발생 지점]
      ▼
TMS Product 테이블                      ← cascade가 실제로 읽는 곳
  견적코드별 박스명칭 + 박스당 제품수 (+ formula CBM ~98% 공백 → 표준표 폴백)
      │
      ▼
cascade S5 출하 CBM 예측                ← 물리 굿즈 96.9% 도달 (PoC 실측)
```

**사본 구조의 실증 (drift 증거)**:
- 단품/키트 박스 스펙을 TMS는 **이름 접미로 임시 분리** — `LSPO 로고스트랩 파우치 (대형/100)` vs `LSPH 로고스트랩 파우치 (키트) (중대형/25)`. NEST는 같은 것을 옵션 레벨 구조로 관리.
- WMS↔TMS 코드 불일치 보정용 하드코딩 alias 8건 + 사이즈군 4건 (`product_alias.py`, "사용자 확정 2026-06-16").
- TMS Product의 박스 CBM formula 필드는 ~98%가 0 (박스사이즈 미입력) — 코드의 표준표(`BOX_TYPE_TO_CBM_M3`)가 사실상 권위.

### 1.2 결론 명제

> **TMS Product 조인은 과도기 경로다. 구조적 요구는 NEST 박스 CBM의 API 노출이다.**

현재 API v1.0 응답에는 부피 재료가 0개 (수량·옵션명·키트구성뿐). 옵션 문자열("박스 사이즈 M")로 표준 부피를 추정하는 우회도 **박스당 입수량이 없어** 출하 박스 수를 못 센다 — 이 빠진 조각이 정확히 NEST 마스터의 "박스단위(개당)"이다.

### 1.3 노출 요구 스펙 초안 (NEST팀 전달용)

`quoteGoods[]` 각 항목에 additive 필드 추가 (하위호환 — /v1.x 배포 가능, 스키마 정책 §11 부합):

```json
{
  "quoteGoodsInstanceId": "...",
  "goodsCode": "DRCG",
  "packaging": {
    "standalone": { "boxName": "특대형", "boxUnitPerPiece": 0.0625 },
    "inKit":      { "boxName": "특대형", "boxUnitPerPiece": 0.0625 }
  }
}
```

- `boxName`: 마스터의 박스 명칭 (극소형/중형/중대형/대형/특대형)
- `boxUnitPerPiece`: 마스터의 "박스단위(개당)" — **의미론 확인 필요**: 박스당 제품수의 역수(0.0625=16개/박스)인지 서면 확인
- `standalone`/`inKit`: 단품·키트 포장 구분 (마스터에 이미 분리 존재)

### 1.4 검증 계획 [확인 필요]

API 미노출 상태이므로 표본 대조는 수동:
- 대표 굿즈 20종 — NEST 마스터 값 (NEST팀 export 또는 화면 대조) vs TMS Product 값
- 측정: 박스명칭 일치율 · 입수량 일치율 → **drift율이 "SSOT를 NEST로 선언"의 정량 근거**
- 다른 접근: 노출이 먼저 수용되면 API로 자동 대조 가능 (검증 비용 소멸)

### 1.5 노출 후 전환 시나리오

| 시점 | CBM 소스 | 역할 |
|---|---|---|
| T0 주문 등록 | **NEST packaging (노출 후)** — 현재는 NEST 키 + TMS 박스스펙 | S5 출하 CBM 예측 · 배차/창고 사전계획 |
| T1 임가공·출하 | Shipment `최종 외박스 수량` (실측) | **확정** — 정산·KPI·Total_CBM (불가침) |
| 피드백 | 실측 − 예측 오차 | 굿즈/키트별 포장 보정계수 학습 → 예측 수렴 |

TMS Product는 정산 레거시·대사 대상으로 강등 (즉시 폐기 아님 — 운임정산 이름매칭 경로가 소비 중).

## Part 2 — NEST 데이터 요구사항 정의 (등급표)

### 2.1 NEST에 요구할 것

| 등급 | # | 항목 | 용도 | 미수용 시 영향 |
|---|---|---|---|---|
| **필수** | 1 | **박스 스펙 노출** (Part 1.3 스펙) | S5 출하 CBM의 NEST 단독화 | TMS 조인 유지 (96.9% — 운영 가능하나 사본 drift 상존) |
| **필수** | 2 | **견적 버전 신호** (`updatedAt` 또는 version) | 견적 변경 감지 → 재조회(T2) | 콘텐츠 해시 자체 구현으로 대체 (비용↑, 이미 설계됨) |
| 권장 | 3 | 벌크 굿즈 카탈로그 endpoint | 크로스워크 자동 시딩, 프로젝트 단위 조회 한계 해소 | 프로젝트별 축적(accretion)으로 대체 — forward-only엔 지장 없음 |
| 권장 | 4 | 박스 마스터 (박스명칭→치수·부피) | 표준표(`BOX_TYPE_TO_CBM_M3`) 이중화 제거 | 코드 표준표 유지 (관리 지점 2개) |
| 권장 | 5 | `expectedReleaseDate` null 정책 확약 | S5 출고 forward 앵커 보조 | 현행 order `출고 요청일` 유지 |
| 선택 | 6 | 견적 확정 웹훅 | cron 대기 없이 즉시 트리거 | cron 3×/day로 충분 (현행) |
| 선택 | 7 | MOQ 노출 | 참고 정보 | 영향 없음 |

### 2.2 NEST에 요구하지 않을 것 (대체 SSOT 확정 유지)

| 데이터 | SSOT | 상태·과제 |
|---|---|---|
| PT 자재 BOM·소요량_개당 | **WMS_BOM** | 연쇄 성공률 90.8% · 검증완료 7% → 검증 캠페인 (안나 협업, NEST 키트 합계로 교차검증 가능) |
| 파츠(PT) 치수 → 입하 CBM | **sync_parts** | 사용자 입력 진행 예정 — 완결률 9%의 병목, 갭의 77% (top-100 PT 우선) |
| 재고 | **InventoryLedger** | 운영 중 |
| 실측 CBM | **Shipment 최종 외박스 수량** | 운영 중 (임가공팀 기재) — 확정값 |
| 주문 수량 | **WMS order** | NEST 견적수량은 대사 신호로만 (실측 median Δ 0.0%) |

### 2.3 Fallback — 요구 미수용 시의 "다른 SSOT 방향"

필수 1·2가 거절될 경우: **경로 B — Airtable 큐레이션 레이어가 박스 스펙 SSOT**
- 박스명칭·입수량을 WMS 크로스워크/ItemMaster에 사본 큐레이션 (기계 제안=미검증, 확정 승급=대사+안나 승인)
- 장점: 런타임 TMS 의존 제거, 우리 통제권. 단점: 수기 관리 부담이 물류로 이전 — NEST 마스터와의 drift를 우리가 떠안음
- 킥오프 L0~L2 "신규 SSOT (백엔드 TBD)" 논의의 실질 안건 — **안나 회의에서 경로 A(NEST 노출) vs B(큐레이션) 결정 필요**

## Part 3 — 자재팀 위치 액션 설계 (베스트원/에이원)

### 3.1 3노드 네트워크 모델 (사용자 확정 운영 규칙)

```
베스트원 (보관 버퍼)          에이원센터 (1차 투입 + ASSEMBLY)      외주 임가공지 (다영기획 등)
STORAGE×2 · IB/OB staging     STORAGE · IB/OB staging · ASSEMBLY   Location 테이블 밖 (외부)
QC_HOLD · QUARANTINE          Max_CBM: IB 57.6m³ (유일 실측)       프로젝트별 동적 지정
      │                              │  ▲                                ▲
      │ ③ 보충 이동(311) ──────────→ │  │                                │
      │ ② 직입하 ────────────────────┼──┼────────────────────────────────┤
      │                              │  └── ① 재이동 (투입분 회수) ──────┘
```

- 임가공지는 **프로젝트별 동적** — 에이원 지정 후 다영으로 변경되는 케이스 실존
- 이동 패턴 3종: ① 에이원→다영 재이동 (투입했던 자재 회수 이동) ② 베스트원→다영 **직입하** ③ 베스트원→에이원 보충
- 베스트원 = 보관창고(버퍼), 에이원 = 기본 투입지 (ASSEMBLY 보유)

### 3.2 S2.5 위치분기 레이어 스펙 (설계 — 구현은 후속 phase)

**위치**: cascade S2(MRP) 직후, S3 앞. 순수 함수 레이어 — `CascadeContext` 주입 패턴 준수.

**입력**:
- `net_requirements` 결과: PT별 gross·재고·shortfall (기존)
- `stock_rows`의 **warehouse별 분해** — 데이터 이미 존재 (`order_cascade.py:147-167`이 Location→Warehouse 로드, 현재는 거점 합산 차감만 함)
- **임가공 목적지** (프로젝트별 입력값 — 기본 에이원, 변경 시 다영 등) [확인 필요: 이 정보가 pkg_schedule/order 어느 필드에 있는지 스키마 실사]

**판정 로직** (PT별):

| 케이스 | 조건 | 제안 액션 |
|---|---|---|
| A | 전 거점 재고 0 | **발주 제안** (PT×수량 발주서 초안) |
| B | 목적지 부족 & 타 거점 보유 | **이동 제안** (from→to×수량, 이동유형 311) — 패턴 ①②③ 중 해당 |
| C | 분산 보유 & 합계 충분 | 통합 이동 제안 |
| D | 분산 보유 & 합계 부족 | 통합 이동 + 잔여 발주 (혼합) |

**출력**: 1단계는 digest/리포트 텍스트만 — PropagationLedger 필드 추가 없음 (INSERT-only 원칙, 필드 신설은 검증 후 cutover 단계). 이동/발주의 실제 기표는 사람이 수행 (제안 자동화 → 기표 자동화는 별도 단계).

### 3.3 자재팀 액션 카탈로그 (주문 등록 시점 타임라인)

| 시점 | 액션 | 근거 데이터 | 상태 |

| 주문 등록 즉시 | **발주 vs 이동 분기 제안** 수신 → 발주서/이동지시 초안 확정 | S2.5 (신설) | 설계 |
