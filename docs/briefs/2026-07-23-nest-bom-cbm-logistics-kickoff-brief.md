## 0. 한 장 요약 (킥오프 핵심 메시지)

> **NEST는 "무엇을 팔기로 했나"를 확정하는 세일즈(CPQ) 시스템이다. 우리가 원하는 "고객 등록 → 자재 → 창고 → 배차 → 운임 마감"의 물류 실행 체계는 NEST가 대신 해줄 수 없다. NEST 확정본을 물류가 번역·전개하는 별도의 SSOT를 세워야 하며, 그 뼈대(cascade)는 이미 돌고 있다.**

- NEST API 실측 결과: 물류가 쓸 **키·수량·키트구성은 신뢰 가능** (수량 괴리 0%, 키 연결 95.8%). 그러나 **자재(PT)·부피(CBM)·재고·실측은 NEST에 없음** — 원래 세일즈 시스템의 영역이 아님.
- 결론: NEST를 **Lv0~Lv2(판매 확정)의 원천으로 수용**하고, 물류가 **Lv3(자재) + 번역기 + 전개엔진**을 세운다.

## 1. 우리 BOM·CBM은 어떤 산업 클래스인가 — "깊이는 얕고, 변동성은 최상위"

BOM 난이도는 **깊이(레벨 수) × 변동성(BOM이 바뀌는 빈도)** 두 축으로 봅니다.

| 축 | 신시어리 | 비교 대상 |
|---|---|---|
| **깊이** | 2~4단 (얕음) | 자동차 7~15단·수천 파츠 / 항공 20단+ |
| **변동성** | **매 주문이 신규 조합** (최상위) | 자동차는 깊지만 BOM이 수년 고정 |

→ **연산 난이도는 쉬운 축, 데이터 거버넌스는 어려운 축.** 우리는 어려운 쪽을 정공법으로 풀고 있으며, 이상한 길이 아닙니다.

**우리와 같은 클래스의 산업 3종** (BOM·CBM 관점):

1. **명절 선물세트 (아모레·LG생건 세트품)** — 시즌마다 단품을 새 조합으로 묶고 세트 전용 포장이 붙음. "단품박스 vs 세트포장, 세트별 CBM" 문제가 우리와 거의 동일.
2. **구독박스/키팅 (HelloFresh·Birchbox·Amazon kitting)** — 매주 바뀌는 얕은 BOM을 대량으로. "키트는 재고로 안 쌓고 주문 시 조립"까지 동일.
3. **Dell식 CTO (Configure-to-Order)** — 고객이 옵션을 골라 **주문 시점에 BOM이 확정**. NEST가 하는 일이 정확히 CPQ(Configure-Price-Quote)이고, production-specification API는 업계 표준 용어로 **"Sales/Order BOM 피드"**.

**SAP 용어 매핑**: 우리 키트 = **phantom assembly**(재고 없이 통과, 주문 시 조립) / NEST 견적 = **Order BOM + Variant Configuration**(옵션이 스펙 결정) / 굿즈→PT = **Production BOM**.

→ 우리가 겪는 고통(53% 조인, 옵션별 CBM, 견적≠실적)도 **이 업계의 교과서적 고통**입니다.

## 2. 4개월 실증 시뮬레이션 요약 (2026-03~06, 1,265 프로젝트 전수)

NEST API + WMS 전체를 읽어 L0~L4 레벨 전개를 돌린 결과. **판정: 레벨 구조 문제없음.**

- **깊이는 L0~L3 4계층이 상한 — L4(원자재 중첩)는 데이터에 없음.** PT가 구매 단위로 종결.
  - 단품 4계층 82.6% / 키트 4계층 9.8% / L3 미도달(BOM 끊김) 7.2% / L2→L3 연쇄율 **90.3%**
- **변동성 프로파일 확정** (업계 클래스 정량 근거):
  - 키트 구성 재사용률 **~0%** (47 시그니처 / 48 키트) — 매번 신규 설계 = 선물세트·구독박스 클래스
  - 굿즈 카탈로그 재사용 **83%** (169종, 최다 32회 재등장) — 안정 부품 × 무한 조합 = Dell CTO 패턴
  - quantityPerKit 172라인 **전부 1.0** / 인쇄 옵션 보유 굿즈 **88.8%** (임가공이 사업 핵심)
- **정합성 양호**: 정체성 drift **0건** / sync 누락 1건(STNB, 기존 쌍둥이 코드) / CBM 도달률 3개월 연속 **97%** 안정
- **NEST 커버리지는 도입 곡선**: 404율 3월 97.8% → 6월 15.7% → **forward-only 통합**이 맞음
- **단품박스째 vs 알맹이 분기는 현행 데이터로 구분 불가**: 키트 소속 굿즈의 포장재 BOM 보유율 72.5% ≈ 단품 69.4% (동률), kitMemo 사용 0건 → **NEST 마스터의 단품/키트 이중 박스스펙 API 노출이 유일한 구조적 해법**. (부수 과제: WMS_BOM 구성유형 공백 63% 백필)

## 3. 계층 구조 비교 — NEST API vs 글로벌 스탠다드(물류 설계)

### ◀ NEST API 콜의 계층 구조 (세일즈/CPQ 뷰)
```
quote (확정 견적)
├─ quoteGoods[]      ← 평면 리스트: 굿즈 + 옵션(사양) + 수량. 깊이 개념 없음
│                      같은 코드가 옵션별 다중 인스턴스로 분화 (instanceId가 관계키)
└─ assemblies[]      ← 키트 묶음: kitQuantity + packageGoods + assignedGoods(참조)
                        수량 불변식 서버 검증 (총 = 키트할당 + 단품)
```
- **핵심**: DAG(그물 구조)는 **NEST에 이미 있음** — 굿즈 한 인스턴스를 키트가 참조하고 잔여는 단품으로. 이 부분은 잘 설계돼 있음.
- **없는 것**: 레벨 의미론, 자재(PT), 전개/롤업, 부피(CBM), 포장 컨텍스트.

### ▶ 글로벌 스탠다드 계층 구조 (물류/제조 뷰)
```
Lv0  출하 유닛 (PNA)              SSOT: WMS order·Shipment │ CBM: 실측 외박스(확정)
Lv1  포장 SKU: 키트(phantom)/단품  SSOT: NEST assemblies    │ CBM: 키트박스 스펙
Lv2  굿즈 변형(옵션지문)           SSOT: NEST quoteGoods     │ CBM: 단품박스 스펙(컨텍스트 분기)
Lv3  자재 PT(구매·재고 단위)       SSOT: WMS_BOM·sync_parts·재고 │ CBM: 파츠 CBM(입하)
```
- **관계**: 이 레벨링은 NEST를 **대체하는 다른 체계가 아니라, NEST(Lv0~Lv2)를 그대로 수용하고 아래로 Lv3·전개수식·CBM 롤업을 더한 상위 설계**.
- 왼쪽 = "무엇을 몇 개 만들기로 했나"의 확정 기록 / 오른쪽 = 그것을 "자재·공간·차량·돈"으로 번역하는 실행 구조.

## 4. NEST API의 취약점·한계 — "세일즈·마케팅용 데이터지, 물류용 데이터가 아니다"

**NEST API 데이터는 신시어리 세일즈·마케팅 부서에 최적화된 데이터이지, 물류팀 실행에 맞는 데이터가 아닙니다.**

| # | NEST의 갭 | 성격 |
|---|---|---|
| 1 | 자재(Lv3) PT·소요량 없음 | **역할 경계** — 글로벌에서도 CPQ는 자재 BOM을 안 가짐 (ERP/MES 몫) |
| 2 | 전개·롤업 의미론 없음 | **역할 경계** — 소비자(물류)가 계산하는 게 표준 |
| 3 | **박스스펙(CBM) API 미노출** | **진짜 갭** — 데이터는 마스터에 있으나 "배송비를 견적에 넣기 위한" 세일즈 목적, API로 안 열림 |
| 4 | **포장 컨텍스트(박스째/알맹이) 미구조화** | **진짜 갭** — 견적 레벨에 없음 |

- 경계 사례: NEST 마스터에 박스 CBM이 있고 견적에 퀵/택배 라인이 붙지만, 목적은 **"배송비를 견적서에 반영"**이지 배차 실행이 아님. **물류 데이터조차 세일즈 관점으로 보유**하고 있다는 증거.
- 처방은 "NEST 불신/교체"가 **아니라**: ① NEST는 잘하는 것(판매 확정)의 SSOT로 승격 ② 실제 갭 2개(박스스펙·포장컨텍스트) 노출 요구 ③ 물류의 실제 갭(Lv3 품질)은 우리가 세움.

## 5. 설계 철학 — "깊이가 아니라 조합"

4개월 표본이 말하는 우리 복잡성의 본질은 **깊이가 아니라 조합**입니다 (키트 재사용 0%, 옵션 88.8% 인쇄, 그러나 계층은 4단 상한).

> **레벨은 4개로 고정하고, 복잡성은 레벨을 늘리는 게 아니라 각 레벨에 붙는 속성 3개로 흡수한다.**
> ① **옵션지문** — CBM 관여 옵션(사이즈·박스종류)만 정체성에 반영, 색상·인쇄색은 제외 (169코드가 수천 변형으로 폭발하는 것 방지)
> ② **포장 컨텍스트** — standalone / in_kit (단품박스 라인의 포함·제외를 라인 속성으로)
> ③ **공정 플래그** — 인쇄·임가공은 레벨이 아니라 BOM 라인의 공정 속성 → M/H·MES 납기로 연결

자동차처럼 레벨을 깊게 파면(인쇄를 레벨로, 단품박스를 레벨로) 우리 변동성에서는 **매 프로젝트 트리 재설계**가 되어버립니다. **얕게 고정하고 속성으로 흡수하는 게 CTO 클래스의 정석**입니다.

**부가 — CBM 3계층 (시점별 역할)**:
- T0 주문 등록 = 견적 박스스펙(NEST≒TMS) → **예측**
- T1 임가공·출하 = 실측 외박스 수량 → **확정** (정산·KPI)
- 피드백 = 실측−예측 오차 → 굿즈/키트별 보정계수 학습

## 6. 물류 실행 SSOT — 무엇을 새로 세우나

**주의**: 새로 세우는 것은 Lv0~Lv2가 **아닙니다**. 그걸 물류가 재구축하면 이중 원천 = 53% 조인 문제의 재생산입니다. 물류가 세우는 것은 4가지 —

| 구성요소 | 현재 상태 | 남은 일 |
|---|---|---|
| **전개 엔진** (cascade) | **운영 중** (S0~S7, cron 3회/일) | 키트 레벨 태깅 + S1.5/S2.5 레이어 |
| **Lv3 데이터** | WMS_BOM 1,702행·ItemMaster·sync_parts 존재 | 검증 7%→↑, PT 치수 입력, 구성유형 공백 63% 백필 |
| **크로스워크 번역기** | 테이블 존재(미소비) | NEST 증거로 채우고 cascade가 읽게 |
| **NEST 수용** | API 검증 완료(PoC) | P1 nest_sync 스냅샷 |

→ 제로에서 시작이 아니라 **뼈대는 이미 돌고 있고, 데이터 품질과 번역 계층만 채우면 됩니다.**

## 7. 지향점 — 고객 등록 → 운임 마감 원스톱 (글로벌 기업형)

```
[고객 주문 등록]
  → NEST 견적 확정 조회 (Lv0~Lv2 수용)
  → S1 키/변형 해석 (크로스워크)
  → S2 자재 전개 MRP (Lv3, WMS_BOM)
  → S2.5 위치분기 (베스트원/에이원 발주 vs 이동 311)
  → S3 입하 CBM·M/H (파츠 치수)
  → S4 창고 적재 투영
  → S5 배차 CBM·wave 예측 (키트 CBM)
  → S6 운임 예상
  → [임가공·출하] 실측 외박스 → CBM 확정
  → [운임 마감] 정산
```
NEST가 채우는 구간 = 등록~S2 진입의 **키·수량·구조**. 물류가 채우는 구간 = **S2 이후 전 구간**. 지금 이 파이프라인이 부분 가동 중이며(완결률 병목은 파츠 CBM 미입력), PT 치수 입력이 최대 레버.

## 8. 킥오프 논의 안건 (제안)

1. **SSOT 경계 확정**: "NEST = 판매 확정 SSOT / WMS·TMS = 물류 실행 SSOT / 크로스워크 = 번역기" 합의
2. **NEST팀 요구 발신**: 박스스펙 API 노출(필수) + 견적 버전 신호 (요구사항 등급표 기 작성 — 설계 브리프 Part 2)
3. **물류 Lv3 캠페인 착수**: PT 치수 입력(최대 레버) · BOM 검증율 · 구성유형 공백 백필
4. **선행 데이터 과제 3건**: 베스트원 Max_CBM 실측 / PT 치수 / 임가공 목적지 필드 실사
5. **역할 분담(RACI)**: L0~L2 수용=물류, L3 검증 승급=품질혁신파트(안나) 협업 여부

---

> **클로징**: "세일즈 SSOT(NEST)는 이미 있다. 없는 것은 물류 실행 SSOT(Lv3 + 번역기 + 전개엔진)다. 그걸 우리가 세운다."
