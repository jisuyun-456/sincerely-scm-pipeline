## 1. 목표 (Goal)

출하 텍스트의 굿즈명이 어떤 철자 변형이든 → **견적코드** → CBM으로 **결정론 조인**되게 하는
크로스워크를 git 데이터파일 SSOT로 구축한다. 퍼지 매칭은 제거하지 않고 **바닥(안전망)으로 남기되**,
확정행이 늘수록 퍼지 의존이 자동으로 줄어드는 구조를 만든다.

### 1.1 북극성 성공기준 (North-Star) — 이것으로 성패를 판정한다

**에이원·다영 출하 `CBM_유효` 완결율 상승** (estimated 경로, 외박스 실측 독립).
단순한 fuzzy→deterministic parity는 성공기준이 **아니다**.

**분모 = 품목 텍스트를 보유한 출하** (텍스트 없는 건은 어떤 매핑으로도 구제 불가하므로 제외).
2026-08-12 전수 실측:

| 거점 | 분모(텍스트보유) | 기준선 | +백필 | +백필+브릿지 | 잔여(마스터부재) |
|---|---:|---:|---:|---:|---:|
| 다영 | 739 | **27.5%** (203) | 79.6% (+385) | **92.8%** (+98) | 7.2% (53) |
| 에이원 | 10,264 | **28.3%** (2,903) | 83.8% (+5,694) | **91.2%** (+762) | 8.8% (905) |

> ⚠️ 핸드오프의 "다영 86.5%"는 **166건 다영 고객납품 CSV** 스코프 값으로, 위 전수 모집단과
> 다르다. 게이트에는 위 표의 전수 기준선을 쓴다.

**커버리지 상승의 출처를 구분한다 (이게 설계 판단의 핵심):**

- **`jaccard_norm` 760건 = 결정론 전환, 커버리지 중립.** 이미 매칭되던 라인이므로 확정행으로
  올려도 완결율은 오르지 않는다. 가치는 *안정성*(퍼지 임계 변동에 흔들리지 않음)이지 커버리지가 아니다.
- **미매칭(<0.5 93건 + 미해소) = 커버리지 순증.** 지금 아무 코드도 못 붙는 라인을 확정행으로
  등재해야 estimated가 **새로 산출**된다. 다영 +98 / 에이원 +762이 여기서 나온다.

**그리고 브릿지 단독으로는 이 지표가 움직이지 않는다.** `CBM_유효`는 *저장된*
`estimated_cbm`을 읽으므로, 확정행을 추가해도 해당 출하분을 **재계산·기록하지 않으면** 필드는
0 그대로다. 현재 두 쓰기 경로가 모두 7일 롤링 윈도우이기 때문이다
(`run_cbm_polling`: 출하확정일 ∈ [today, +7] / `replay_outbound_cbm --recent 7`).
→ **P1 범위 = 크로스워크 + 과거분 백필** (사용자 승인 2026-08-12).

지배적 레버가 백필(6,079건)이고 브릿지 순증(860건)은 그 1/7 규모라는 점을 명시해 둔다 —
게이트 판정 시 두 기여를 분리해 읽어야 한다.

**게이트 판정 (P1 종료 조건):**
- **필수**: 다영 ≥ 79%, 에이원 ≥ 83% (백필 기여분이 정상 반영됐는지)
- **목표**: 다영 ~93%, 에이원 ~91% (브릿지 확정행 승급까지 반영 시)
- 목표 미달 시 실패로 보지 않는다 — 브릿지 기여분은 사람의 확정 승급 속도에 종속되며,
  잔여 7~9%는 Product 마스터 부재(P2 규격요청) 몫이다.
- 단서: 백필은 `fuzzy_write_decision`의 `FUZZY_MIN_CONF=0.5` 게이트를 통과한 건만 기록되므로,
  실제 반영분은 6,079건보다 작을 수 있다. dry-run 수치로 확인 후 판정한다.

## 4. 아키텍처 — 리졸버 통합 (핸드오프 §5 섹션 3)

### 4.1 삽입 위치

`harness/backbone/product_alias.py::resolve_product_entry`, 1단 직후·2단 직전:

```
1)   code 직접 (+ALIAS/SIZE_FAMILY)   → 'code'
1.5) CROSSWALK 조회  ★신규             → 'crosswalk'    ← 확정 ∧ 굿즈명 행만
2)   name → sync_item name2code       → 'name2code'
3)   Jaccard 폴백                      → 'jaccard'
4)   정규화 재시도                      → 'jaccard_norm'
```

1.5단이 2단보다 앞인 이유: 크로스워크 확정행은 **사람이 검증**한 판정이고 `sync_item`은 자동
매핑이므로, 사람 판정이 우선한다.

`method` 반환값에 `'crosswalk'` 추가. 기존 값 5종은 불변 → `measure_cbm_coverage.py`의
`("jaccard","jaccard_norm")` 필터는 영향 없음.

### 4.2 조회 키 — 정규화 + 충돌 검출 (핸드오프 §5 지시 보정)

핸드오프 §5는 정규화 키로 `keys.normalize_goods`를 지정했다. 그대로 쓰면 `(단품)`·`(키트)` 등
변형이 **한 키로 뭉개져**, 서로 다른 견적코드를 가리킬 때 조용히 last-wins 한다 — 결정론이
목표인 테이블에서 치명적이다. 반대로 raw 문자열을 키로 쓰면 변형 760개가 각각 행을 요구한다.

**채택(2026-08-12 개정 후): raw 키(괄호 보존) + 로더의 충돌 검출 의무화.**

- 인덱스 키 = `표준키`의 **공백 제거 + casefold**. `normalize_goods`를 쓰지 **않는다**.
- `표준키` 컬럼에는 **사람이 읽을 raw 형태를 그대로 저장**(리뷰 가독성)
- 같은 인덱스 키에 **서로 다른 `TMS_견적코드`를 가진 `확정` 행이 둘 이상**이면 충돌로 판정한다.
  조용한 last-wins 금지.

#### 왜 `normalize_goods`를 버렸나 — 초기 채우기 실측이 반증 (2026-08-12)

초안은 컴팩트함을 이유로 `normalize_goods` 키를 채택하고 "변형은 같은 코드로 수렴한다"고 가정했다.
**Task 4 초기 채우기에서 이 가정이 반증됐다** — 충돌 27건이 전부 동일 패턴이었다:

```
Simple슬라이드지퍼백(S)/(M)/(L)   → SLZS / SLZB / SLZL   ← 사이즈별 다른 박스·다른 CBM
Solid스탠다드G형박스(S/M/L사이즈)   → SOLA / SOLB / SOLC
퍼블랭킷(무릎담요)/(일반담요)        → FUBL / FUBM
풀커버스티치노트(300개이하)/(초과)   → FCSF / FCSN
캔버스피크닉매트(1인용)/(2인용)      → PCMT / PCMU
```

**괄호 안이 곧 SKU 구분자**다. `normalize_goods`는 `(...)`를 제거하도록 만들어졌으므로(BOM 매칭용
설계) 이 구분을 파괴한다. 이들은 철자 변형이 아니라 **서로 다른 제품**이다.

실측 비교(확정 708행 기준):

| 인덱스 키 | 키 수 | 충돌 | 결정론 사용가능 |
|---|---:|---:|---:|
| `normalize_goods` (초안) | 502 | 27 | 475 |
| **raw 공백제거+casefold (채택)** | 567 | **1** | **566** |

정확성과 커버리지가 **동시에** 개선된다(+19%). 초안이 우려한 "행 수 증가" 부담은 실재하지 않았다 —
후보 생성기가 이미 출하 텍스트의 고유 이름마다 1행을 만들기 때문에 행 수는 어느 쪽이든 같고,
`normalize_goods`는 *인덱스 시점에만* 그것들을 뭉개서 정보를 잃고 있었다.

부수 효과 하나는 의도된 것이다: 미등재 신규 변형(예 `데일리짐색(신규포장)`)은 이제 결정론으로
해소되지 않고 퍼지(3·4단)로 흐른다. 27건이 증명하듯 괄호 변형은 다른 제품일 때가 많으므로,
베이스 코드로 결정론 매핑하는 것보다 점수가 붙는 퍼지로 보내는 편이 안전하다 — Q2 안전망 설계와 일치.

충돌 검출은 `확정` 행에만 적용한다(미검증·보류는 결정론 맵에 적재되지 않으므로 오동작 불가).

#### 충돌 시 동작 — 런타임과 검증을 분리한다 (2026-08-12 개정)

초안은 "로드 시점 hard error" 단일 방식이었으나, 리뷰에서 **런타임 raise가 더 위험**함이 드러나
아래로 개정한다.

| 경로 | 동작 | 이유 |
|---|---|---|
| `load_crosswalk()` — 런타임 | **충돌 키를 양쪽 다 제외** + 경고 로그. raise 안 함 | 아래 3가지 |
| `validate_crosswalk()` — 검증 | **`CrosswalkConflictError` raise** | 사람이 파일을 고치는 시점에 loud 실패 |

런타임에서 raise하면 안 되는 이유:
1. `resolve_product_entry`는 **라인당** 호출된다(전수 약 19.7k 라인). 그런데
   `tms_settlement/calc.py:243`이 `except Exception: pass`로 감싸고 있어 예외가 **조용히 삼켜지고**
   `cbm_unload`가 0으로 저하된다 → **기사님 상하차비 과소지급이 신호 없이 발생**.
2. `simulate_park_dayoung_cbm.py:165`·`backfill_상하차비용.py:153`은 try 자체가 없어 **배치가 중단**된다.
3. 예외 경로는 캐시에 도달하지 못하므로 **매 호출 전체 CSV를 재파싱**한다(핫루프 성능 붕괴).

**거버넌스 의도는 오히려 강화된다** — 충돌 키는 어느 쪽 코드도 채택되지 않고 결정론 맵에서 통째로
빠진다. 그 결과 해당 굿즈명은 Q2가 설계한 퍼지 안전망(3·4단)으로 흐른다. "결정론적으로 알 수 없는
것은 결정론으로 취급하지 않는다"는 원칙에 정확히 부합한다.

검증 시점(Task 4 게이트, 향후 CI)에는 `validate_crosswalk()`가 raise하므로, 충돌은 **사람이 파일을
수정하는 그 자리에서** 드러난다 — FGPS 류 진짜 충돌이 묻히지 않는다.

### 4.3 로더 계약

```
load_crosswalk(path=None) -> dict[str, str]     # 정규화키 → 견적코드(upper)
```

- 필터: `검증상태 == 확정` ∧ `키유형 == 굿즈명`
- **프로세스 단위 캐시** (리졸버가 라인당 호출되므로 매회 파일 IO 금지)
- **파일 부재 → 빈 dict 반환**, 1.5단 자동 무력화 → 기존 1~4단 동작과 완전 동일 (안전 기본값)
- `표준키` 또는 `TMS_견적코드`가 공백인 행은 skip + 카운터 집계
- 크로스워크가 가리키는 견적코드가 Product에 없거나 CBM 0이면 → 1.5단이 반환하지 않고
  통과(아래 4.4) + **stale 카운터** 집계(감사용)

### 4.4 CBM 조인 경로

```
견적코드 → load_product_lookup entry → box_type → BOX_TYPE_TO_CBM_M3 → cbm_per_box
```

1.5단도 **1·2단과 동일하게 `cbm_per_box > 0` 가드**를 적용한다. CBM 없는 Product를 가리키는
확정행이 0짜리 entry를 반환해 하위 계산을 오염시키는 것을 막고, 대신 퍼지 단계로 흘려보낸다.

## 6. 채우기 + 리뷰게이트 (핸드오프 §5 섹션 4 · P1 프리뷰)

### 6.1 산출물

| 파일 | 내용 | 인코딩 |
|---|---|---|
| `data/crosswalk/goods_crosswalk.csv` | SSOT (확정 + 미검증) | UTF-8 |
| `data/crosswalk/pending_specs.csv` | 보류 = 규격요청 리스트 (품질혁신파트 전달) | UTF-8-SIG (Excel 대비) |

### 6.2 후보 진입 규칙 — measurement 세션 실측 시드 (핸드오프 §6)

| 소스 | 규모 | 진입 `검증상태` | `매칭방식` |
|---|---|---|---|
| `jaccard_norm` score = 1.0 | 760 중 다수 | **확정** (자동, D2) | `정확` |
| `jaccard_norm` score < 1.0 | 나머지 | `미검증` → 사람 승급 | `유사` |
| `jaccard` score < 0.5 | 93 | `보류` → 규격요청 | `유사` |
| 미해소 이름 빈도표 | `프리미엄스트링후드집업(F` ×93, `Raw코튼파우치(L` ×63 … | `보류` → 규격요청 | `수기` |

빈도 내림차순 정렬로 우선순위를 부여한다(무엇부터 등재/요청할지).

### 6.3 멱등성 — 핵심 안전장치

**생성 스크립트는 기존 행을 절대 덮지 않는다. 신규 `표준키`만 append.**

사람이 `미검증 → 확정`으로 바꾼 판정이 재실행으로 되돌아가면 거버넌스가 무너진다. 따라서
파일 수준의 **INSERT-only** 원칙을 적용한다(운영 원장의 Immutable Ledger 원칙과 같은 취지).
기존 행의 어떤 컬럼도 스크립트가 수정하지 않으며, 재실행은 항상 안전하다.

### 6.4 리뷰게이트

사람이 CSV의 `검증상태`를 `미검증 → 확정`으로 수정 → 커밋 → **PR diff가 곧 리뷰 산출물**.
(CSV를 고른 이유가 이것 — JSON은 diff에서 판정이 묻힌다.)

## 7. 테스트/검증 (핸드오프 §5 섹션 5)

1. **결정론** — 같은 입력 → 같은 견적코드 (반복 호출·프로세스 재시작 무관)
2. **충돌 처리** — 같은 정규화 키·다른 견적코드의 `확정` 행 2개일 때:
   `load_crosswalk()`는 그 키를 **양쪽 다 제외**하고 경고만(raise 금지),
   `validate_crosswalk()`는 **raise**한다 (4.2 개정)
3. **확정만 결정론** — `미검증`·`보류` 행은 1.5단이 절대 사용하지 않음
4. **파일 부재 안전** — 크로스워크 없으면 기존 1~4단과 완전 동일 동작
5. **CBM 가드** — 확정행이 CBM 0 Product를 가리키면 1.5단 통과 → 퍼지 폴백 (4.4)
6. **북극성 — `CBM_유효` 완결율** (§1.1 게이트): 분모=텍스트보유 출하.
   다영 27.5% → ≥79%(필수)/~93%(목표), 에이원 28.3% → ≥83%(필수)/~91%(목표).
   백필 기여분과 브릿지 기여분을 **분리해 보고**한다.
7. **멱등성** — 생성 스크립트 2회 실행 → 파일 바이트 동일, 사람 판정 보존 (6.3)
8. **이관 parity 골든** — 현재 ALIAS/SIZE_FAMILY 해소 결과를 골든으로 고정 →
   P2 이관이 동일성을 증명할 수 있게 함 (D1의 전제조건)

## 8. 비목표 (Non-Goals)

- **ALIAS/SIZE_FAMILY/SYNTHETIC 이관** — P2 (D1). P1은 딕셔너리 그대로 유지.
- **`키유형=코드`·`파츠` 행 소비** — 스키마에만 존재, P1 미사용.
- **CBM 값 저장** — 크로스워크는 신원 매핑만. Product가 CBM SSOT.
- **Airtable `WMS_KeyCrosswalk` 갱신** — 소비처 0인 죽은 자산. 되살리지 않음.
- **`WMS_ItemMaster` 재적재** — 굿즈행 소비처 0 + 재적재 시 파츠 351행 파괴. 무관.
- **퍼지(3·4단) 제거** — Q2상 안전망으로 유지. 확정행 증가로 자연 축소되게 둔다.
- **Product 마스터 정리**(FGPS·dup/junk) — chain P2. §1.1의 잔여 7~9%(마스터 부재)가 여기 해당.
- **파서 잔해 교정** — `XL사이즈)키트`·`Raw코튼파우치(L` 류는 `(S/M/L/XL사이즈)`를 `/`로 분할하며
  생긴 파싱 잔해다. 크로스워크 확정행으로 덮으면 잔해를 SSOT에 영구 등재하게 되므로
  **크로스워크로 처리하지 않는다**. `parse_product_lines_v2`의 분할 규칙 문제로 별도 과제.
  (단 `키트`·`+인쇄` 접미는 실제 굿즈명 변형이므로 크로스워크 대상이 맞다.)
- **입하 CBM(S3)·BOM 소요량 전파** — 병목이 PT 자재 규격(치수) 데이터 부재이고 축이 PT 단위라
  굿즈명 크로스워크와 무관. 캐스케이드 완결의 남은 조각이지만 본 설계 범위 밖.

## 9. 리스크

- **오매칭의 SSOT 영구박제** — 자동 확정이 틀리면 결정론으로 굳는다. 완화: score 1.0(정규화 후
  exact)만 자동확정(D2), 나머지는 사람 게이트. 추가로 `근거` 컬럼에 출처·score를 남겨 사후 추적 가능.
- **정규화 키 충돌** — 4.2의 hard error로 조용한 오염을 차단. 단 **첫 채우기 때 대량 충돌이
  드러날 수 있다** — P1은 이를 실패가 아니라 규격요청 대상으로 처리해야 한다.
- **캐시 staleness** — 프로세스 단위 캐시라 장기 실행 프로세스는 파일 변경을 못 본다. 현재
  소비자는 모두 단발 실행(cron·스크립트)이라 무해. 장기 프로세스 도입 시 재검토.
- **정산 금액 영향** — 1.5단이 기존 퍼지 결과를 **다른 코드로** 바꾸면 CBM·상하차비가 변한다.
  P1 검증에서 변경 전/후 delta를 산출하고 사람이 승인해야 한다(선행 세션과 동일한 게이트).

## 10. 롤백

크로스워크 파일 삭제 또는 전 행 `검증상태≠확정` → 로더가 빈 맵 반환 → 1.5단 무력화 →
기존 1~4단 동작으로 완전 복귀. 코드 롤백 없이 데이터만으로 되돌릴 수 있다(4.3의 안전 기본값).
